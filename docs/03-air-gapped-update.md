# 03 · 单向更新到受限环境（A → C）

> C 端是**没有 terminal 的 JupyterLab**：不能开命令行、不能 git、不能 chmod、不能解压。
> 能做的只有：创建/上传文件、打开 notebook、运行代码。
> 所以更新方式只能是：**上传一个压缩包 + 跑一个写好的 notebook**。

---

## 0. 整体流程

```
   A 端                                   C 端
   make-update-package.sh  ──tar.gz──▶   上传到 JupyterLab
   （git archive 导出代码）                打开 C-update.ipynb
                                         Run All Cells
                                         Restart Kernel
```

只往 C 送，C 从不往回传。C 端改了代码也不会回流，下次更新会被覆盖。

---

## 1. 一次性准备（只做一次）

### 1.1 把 `C-update.ipynb` 传到 C 端

在 C 的 JupyterLab 里，把 `C-update.ipynb` 上传到一个**你记得住的目录**。建议就放在代码目录的上一级，或者直接放代码目录里。

> 找不到上传按钮（左上角向上箭头 / 拖拽文件）：说明 C 端把上传也禁了，告诉我，换共享目录方案。

### 1.2 填两个绝对路径（重点，只填一次）

打开 `C-update.ipynb`，看第 1 格，里面有两个变量，都是**空着等你自己填的绝对路径**：

```python
DEST    = "/path/to/myproject"   # 代码要更新到哪个目录
PKG_DIR = "/path/to/package_dir"       # 上传的包放在哪个目录
```

`/path/to/...` 只是示例，不改的话第 1 格会直接告诉你「这些路径还不能用」。

**怎么拿到路径**：什么都不用猜，先按原样跑一次第 1 格。它会打印当前目录，而 notebook 默认就在自己所在的目录里，所以打印出来的这行八成就是你要的路径，直接照抄进去：

```
Python   : 3.11.6
当前目录 : /home/jovyan/work
目标目录 : /path/to/myproject
包目录   : /path/to/package_dir

[要改] 这些路径还不能用：DEST、PKG_DIR
       如果当前目录就是你要的目录，把它照抄上去，例如：
         DEST    = r"/home/jovyan/work"
         PKG_DIR = r"/home/jovyan/work"
```

把包上传到哪个目录，`PKG_DIR` 就填哪个（包和 notebook 放一起最省事，两个填一样即可）。改完再跑一次第 1 格，看到 `[OK] 两个目录都存在` 就对了。

然后跑第 2 格，它会把目标目录的内容列出来，确认里面能看到 `models/`、`config/`、`process/` 这些——这才是代码目录。如果列出来是个空目录或者不对，说明 `DEST` 填到别处去了，回去改。

> **注意**：C 端环境禁用了一些库，这个 notebook 已经全部避开——**`pathlib`、`tarfile`、`shutil`、`glob` 都不用**，
> 只依赖 `os` 和 `zlib`/`gzip` 这两个最基础的模块。
> 路径直接写绝对路径字符串，不需要包任何东西；解包是自己按 tar 格式拆的，
> 不用装任何包，也不需要系统里有 tar 命令。

### 1.3 首次更新前，先把现有代码备份一份

第一次会覆盖全部已有代码。稳妥起见，先在 C 端跑这一段（新建一个 cell）：

```python
import os, shutil, time
src = os.path.realpath(DEST)
bak = src + "_before_update_" + time.strftime("%Y%m%d-%H%M%S")
shutil.copytree(src, bak)
print("已备份到:", bak)
```

数据多的话这一步会慢，但只做一次。

## 2. 每次更新（日常就这几步）

### 第一步：A 端打包

```bash
~/make-update-package.sh \
  -r /srv/project \
  -o ~/Desktop
```

`-r` 是仓库目录，`-o` 是输出目录，两个都可以按需改，**不用先 cd 进仓库**。仓库和输出都固定的话，直接存成别名：

```bash
echo "alias cpkg='~/make-update-package.sh -r /srv/project -o ~/Desktop'" >> ~/.bashrc
# 之后每次只敲：cpkg
```

也可以只给分支，或指定别的分支：

```bash
~/make-update-package.sh -b dev -o ~/Desktop
~/make-update-package.sh -r <仓库> -b uat -o /tmp
```

老写法仍然能用（第一个参数是仓库目录就当仓库，否则当分支）：

```bash
cd <仓库> && ./make-update-package.sh dev ~/Desktop
```

产物两个文件，放在一起：

```
c-update-20261030-ac2c319.tar.gz
c-update-20261030-ac2c319.tar.gz.sha256
```

包名里的 `ac2c319` 就是这次更新对应的 commit，出问题时好回溯。同一个 commit 同一天重复打包，会自动加时分秒后缀，不会覆盖也不会报错。

### 第二步：上传到 C 端

把上面**两个文件**一起拖进 C 端 JupyterLab，放到 `PKG_DIR` 指的那个目录（第 1 格填的），默认就是 `C-update.ipynb` 所在目录。

### 第三步：跑 notebook

1. 打开 `C-update.ipynb`
2. **第 1 格不用再改**（路径已经存好了）；直接 `Run` → `Run All Cells`
3. 看到这样的输出就成功了：

```
使用包  : c-update-20261030-ac2c319.tar.gz (12 KB)
sha256  : 校验通过
解压中  : 正在读取 c-update-20261030-ac2c319.tar.gz
包内条目: 187
已备份 24 个旧文件 → _backup_20261030-153518
解压完成: 163 个文件
清理 __pycache__: 9 个
权限已刷 777: 213 个条目
================================================
更新完成
```

几个数字怎么看：

- **包内条目 187 ≠ 解压完成 163**：条目数包含目录（`models/`、`config/` 这些），文件数只算文件，差的就是目录数，正常。
- **已备份**：这次被覆盖掉的旧文件数量。第一次更新会很大（几乎全仓），之后会小很多。
- 只要最后出现 `更新完成` 那一行，中间这些数字不需要核对。

4. 菜单 `Kernel` → `Restart Kernel`（**必须做**，否则跑的还是旧代码）

### 第四步：验证

打开平时用的那个 notebook，从头跑一遍，看结果正常。

## 3. 它到底做了什么

| 步骤 | 动作 | 为什么 |
|:--:|---|---|
| 1 | 找目录里最新的 `c-update-*.tar.gz` | 不用记文件名 |
| 2 | 校验 sha256 | 防止上传过程文件损坏，坏包直接拦下 |
| 3 | 检查包内路径不许跳出目标目录 | 防止写坏别的目录 |
| 4 | 把将被覆盖的旧文件复制到 `_backup_时间/` | 可回退 |
| 5 | 解压覆盖 | **只覆盖同名文件，不删除任何东西** |
| 6 | 清掉 `__pycache__` | 否则可能加载旧字节码，改了代码却没生效 |
| 7 | 全部权限刷 777 | jupyter 容器只认 777 |
| 8 | 打印结果 | 一眼确认 |

关键点：**只覆盖、不删除**。C 端独有的文件（数据、日志、`_backup_*`、自己加的脚本）一个都不会少。

---

## 4. 三条规矩

1. **不要在 C 端改代码。** C 没有 git，改动回不来；下次更新会被 A 的版本覆盖。要改让 A 改。
2. **一次只传一个包。** 目录里堆多个包时，脚本按修改时间取最新的；万一取错就白跑一遍。
3. **跑完一定 Restart Kernel。** 否则你会盯着旧结果怀疑人生。

## 5. 出错对照表

| 屏幕上的字 | 原因 | 怎么办 |
|---|---|---|
| `[要改] 这些路径还不能用` | `DEST` / `PKG_DIR` 还是示例值 | 照第 1 格打印的当前目录填上去 |
| `没找到 c-update-*.tar.gz` | 包没上传，或传到了别的目录 | 确认包在 `PKG_DIR` 指的那个目录里 |
| `sha256 不匹配` | 上传中文件损坏 | 重新上传一次 |
| `不是 gzip 文件` | 传错了文件，或包没传完整 | 重新上传 `.tar.gz` 本体（别传 `.sha256`） |
| `解压失败，包可能已损坏` | 包体残缺 | 删掉重新上传 |
| `包里没有文件` | 包损坏或不是本工具的产物 | 回 A 端重新生成 |
| `目标目录不存在` | `DEST` 路径写错 | 回第 1 格改 |
| `包内含指向目录外的路径` | 包不对劲 | 回 A 端重新生成 |
| 跑完结果还是旧的 | 没重启内核 | `Kernel` → `Restart Kernel` |
| 想回退到更新前 | 需要旧代码 | 打开 `_backup_时间戳/`，把文件拷回去 |

> **关于解包怎么做的**：C 端禁用 `tarfile`，所以 notebook 里自带一个极简 tar 解析器（约 80 行），
> 只用 `gzip`（万一也被禁，自动退回 `zlib` 手解）解压，然后按 512 字节块自己拆包。
> 已覆盖 git 产出的全部情况：普通文件、目录、超过 100 字节的长路径
> （ustar prefix / pax 扩展头 / GNU 长名 三种写法都支持）、中文文件名。
> 包里的符号链接、设备文件会被跳过，不会写到磁盘上。
> 全程不依赖 `tarfile`、`pathlib`，也不需要装任何包、不需要 tar 命令。

## 6. 两个已知限制

**① 数据文件不在包里。**
包里只有 git 里登记过的代码。`docs/` 下的 `index_data`、`stylePB`、`PE_TTM`、`macro_data_raw`、`PolicyRateBand`、`Bond_detail_*.xlsx` 都不会被更新——C 端原有的数据保持不动。如果数据也要更新，那是另一条通道（文件太大，不能走这个包），需要单独商量。

**② C 端的改动没有回流通道。**
C 没有 terminal，跑不了 git，所以 C → A 只能靠人：把改过的文件手工下载下来发给 A，由 A 手动合并。真要长期在 C 上开发，得给 C 开 terminal 或挂共享目录。

## 7. 文件清单

| 文件 | 放哪 | 作用 |
|---|---|---|
| `make-update-package.sh` | A 端任意目录（建议 `~/`，不必放仓库里） | 生成更新包 |
| `C-update.ipynb` | C 端 JupyterLab（一次性上传，长期复用） | 解压更新 |
| `c-update-*.tar.gz` | 每次上传到 C 端 | 这次的代码 |
| `c-update-*.tar.gz.sha256` | 和包一起上传 | 校验用 |
